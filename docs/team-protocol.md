# 团队协作协议

权威运行规则在 agents/common.md，导出工具会把它拼入每个角色指令。本文帮助团队配置和理解这些规则。

## 决策边界

| 事项 | 决策/负责者 | 其他角色的职责 |
|---|---|---|
| 产品目的和范围变化 | 人类；Planner 整理问题 | 提供影响证据 |
| 已授权范围内的技术路线、跨端语义 | Planner | 两端提供可行性和影响评估 |
| 局部实现、内部结构、常规测试 | 对应 Lead | 不必逐项等待 Planner |
| 困难算法、跨端根因、连续失败 | Planner | 提交复现、假设和已尝试方法 |
| 单领域子任务汇总 | 对应 Lead | 遵守共同契约 |
| 跨角色合并、联调、业务验收 | Planner | 修复领域内问题并更新交接 |
| 正式评审 | 独立 Reviewer | 作者自检和修复；不自审通过 |

## 状态与恢复

READY → IN_PROGRESS → IN_REVIEW → READY_FOR_INTEGRATION → INTEGRATING → ACCEPTED。

这是团队协议状态，可记录为任务字段/正文；不要求平台存在同名状态枚举。BLOCKED 保存原阶段、阻塞依赖、负责人、下一步，解除后回到原阶段。评审失败回到实现；契约/代码变更重开受影响阶段。Lead 不设置整个功能的 ACCEPTED。

每次交接带任务 ID/版本、契约版本、工作区、base/head 或可重建 patch、结果和日志位置、评审身份/覆盖版本、阻塞与下一步。消息只传递记录定位符，不替代记录。恢复时核对实际 Git 状态和仍在运行的 worker，避免重派和重复合并。

一个记录只有一个写入负责人。任务负责人写自己的任务记录；Planner 写功能索引和集成记录。共同槽位通过原子更新或 Planner 串行授权分配，避免三个角色分别以为还有全局余量。

## 何时升级

改变共同契约/业务语义、影响另一角色、缺少必要信息、需要高风险架构判断，或两轮没有有效进展时，提交 Planner。升级记录必须说明期望/实际、候选版本、复现、已尝试假设、证据及具体待决问题。Planner 接手困难部分，保持无依赖任务继续执行。

## 交付标准

领域交付：实现符合契约、领域必需检查通过、独立规格和质量评审通过。Mock 仅证明相应前端行为，不能证明真实后端联通。

功能交付：Planner 在明确的组合版本上完成必要的构建/测试、真实联调与业务验收，并获得覆盖该版本的独立评审。缺失环境、未运行、跳过、失败均明确记录；不能通过改写状态名称掩盖缺口。

验收不自动授权生产部署、对外发布、破坏性迁移或删除源分支。
