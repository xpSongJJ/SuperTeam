# 交付演练：订单创建

以下是可执行流程示例，不是已完成的业务测试结果。把命令、路径和版本替换为目标项目的真实值。

1. **Planner 明确目标。** 用户提交商品后，需要看见已持久化的订单；重复提交不得产生第二笔订单。定义成功、失败、网络重试、会话失效和跨租户访问验收案例。
2. **共同契约 v1。** 金额使用整数分；成功响应代表事务已提交；客户端重试使用同一请求身份；服务端按租户验证访问权。两端 Lead 确认可实现。Planner 负责决定幂等和持久化边界。
3. **分派。** FE-1 负责表单/状态/请求身份/键盘交互；BE-1 负责接口/事务/授权/并发测试。Planner 拥有困难幂等算法和 INTEGRATE-1。任务引用契约版本，分配独立工作区，数据库迁移索引给后端单一负责人。
4. **实现与评审。** 各 Lead 可派实现、测试和 Reviewer 子 Agent；Reviewer 不参与所审代码的编写。返回代码版本和实际测试输出。领域通过后才 READY_FOR_INTEGRATION。
5. **故障注入。** 假设后端仅入队就返回成功。前端不得修改 mock 隐藏差异；Planner 对照目标决定修正实现或向人类提出需求变化。变更契约时更新依赖任务和失效证据。
6. **Planner 集成。** 固定两端版本，合入集成工作区。运行真实服务和存储，验证刷新后订单仍存在、重复请求只产生一笔订单、会话过期和跨租户请求被正确处理。为每个验收条件保存环境、版本、结果和日志。
7. **独立验收评审。** Reviewer 检查组合版本和 Planner 的冲突修复/关键算法。Planner 根据证据设置 ACCEPTED；测试未运行或评审缺失则保持待处理。
8. **恢复演练。** 中断后新一轮先读记录并核对提交；已完成的任务不重派，旧版本的测试不能继承为新版本通过。

额外反例：让 worker 请求创建孙 Agent、让 Planner 自审、让 mock 结果冒充真实联调、让过期评审覆盖新提交。预期均被识别并保留正确的待处理状态。
